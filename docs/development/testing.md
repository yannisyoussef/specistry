# Test strategy

## Principles

Tests assert semantics, invariants, diagnostics, security boundaries, and user behavior. Snapshots are limited to stable serializations or visual baselines and never substitute for intent. Fixtures include realistic contracts and adversarial structures. Randomized tests use recorded seeds.

SPEC-001 includes a committed canonical v1 golden artifact, a clean public-consumer
type contract, a recorded-seed permutation test, compatibility rejection for future
versions, hostile structure/limit cases, and broad/deep registry performance smoke
coverage.

## Fixture corpus

`tests/fixtures/openapi` contains OpenAPI 3.0/3.1 sentinels, a realistic 3.1 contract (`basic-3.1.yaml`: servers with variables, every security scheme kind, OR-of-AND requirements, multipart/form/binary/empty bodies, headers, ranges, tuples, boolean schemas, `const`, type unions, cycles), a deliberately invalid 3.0 companion (`basic-3.0.yaml`, whose valid subset is covered by `pairs/` and the matrix rows), paired dialect fixtures (`pairs/`), JSON/YAML equivalents, a multi-file reference tree (`refs/`: sibling, nested, parent traversal within the root, self-reference, direct and indirect cycles), recursive and polymorphic schemas, invalid references, and adversarial inputs (`adversarial/`: root escapes including encoded traversal, absolute, `file:`, protocol-relative and remote references, missing files, anchors, duplicate operation IDs, unsupported/future versions, malformed YAML and JSON, duplicate keys, alias bombs, terminal controls and script-looking text, webhooks/callbacks/links, invalid shapes, reference chains that cycle, overflow, or land on the wrong kind of value). Inline cases in the adapter tests cover type arrays, type-less schemas, `$ref` siblings, implicit discriminators, limits, and identity collisions.

Large generated fixtures (`tests/performance/ingestion-generator.mjs`) declare deterministic construction parameters rather than committing megabytes of repetition.

`tests/fixtures/content` holds the authored-content projects: `edge` (every authoring mistake with an expected location: missing and unknown frontmatter, a body H1, expressions, raw and inline HTML, ESM, unknown and misplaced components, invalid props, forbidden link schemes, missing link targets and anchors, missing, unsupported, escaping and absolute assets, a route collision, an invalid file name, a navigation entry for a missing page, and an orphan) and `navigation` (nested sections, a renamed page, a labelled API node, an external link, a folder index page, an orphan warning, an image, Steps, Tabs, Cards, and a table). The TestInbox reader fixture additionally carries nine authored pages, a logo, a favicon, and an accent so the browser and visual suites exercise the composed reader. Fixture pages are Prettier-ignored because their bytes, lines, and columns are what the tests assert.

`tests/fixtures/reader` holds the reader acceptance projects: `testinbox` (a production-realistic 25-operation contract across six tags with path/query/header/cookie parameters, JSON, form, and multipart bodies, body-less and ranged responses, response headers, API-key/bearer/OAuth/mTLS requirements with AND and OR, a deprecated operation, an operation without `operationId`, and nested schemas) and `edge` (hostile strings, a hostile server URL, tag and operationId slug collisions, untagged operations, HEAD/OPTIONS, a very long path and identifier, fourteen parameters, ten responses, anonymous access, every schema shape, and a warning-bearing callback). Each commits its `.specra/artifacts`; `tests/reader/fixtures.test.ts` rebuilds them through the packaged CLI and fails on any byte drift, so the reader is always tested against exactly what `specra build` produces. Nothing in the reader branches on the TestInbox name.

## CI grouping

The fast job runs formatting, lint, types, semantic tests (including actual CLI subprocess and clean-room package execution), architecture, security, dependency-manifest, license, and redacted secret checks. Performance evidence runs in a dedicated job after the build job (`pnpm test:performance`, `vitest.performance.config.ts`) because its cases spawn fresh processes and multi-second workloads; they are excluded from the fast run and from coverage. The clean-room case stages a self-contained CLI tree under a canonical (real-path) temporary directory, asserts normalized non-escaping archive paths and one Zod copy, requires warning-free offline installation, checks the packed Node engine contract, and exercises both binary and programmatic APIs. The canonical directory matters: npm silently omits bundled dependencies when the staged root is reached through a symlink, which is the archive shape the topology assertion rejects. Build/coverage/audit and browser/axe jobs run after it. A dedicated frozen-install/manifest/license/audit dependency-policy job runs only for pull requests. Future visual shards begin when stable reader states exist; they do not block the fast feedback path.

Coverage enforces an 80% statement/line, 75% branch, and 90% function repository floor plus stricter CLI package floors of 85% statements/lines, 75% branches, and 95% functions. `pnpm typecheck` builds the CLI's workspace dependencies (`@specra/model`, `@specra/config`, `@specra/openapi`) first because packages resolve each other's types through built declarations, exactly as `pnpm test` builds the CLI and config before the focused CLI tests. The compiled executable shim and config-process host module are excluded from in-process source instrumentation because they run in subprocess realms; actual executable, config-process failure, timeout, cancellation, output, serialization, secret, and clean-room cases cover those boundaries behaviorally.

## Reader tests and visual baselines

`tests/reader` covers the projection layer (slugs, collisions, route resolution, response order, parameter grouping, security semantics, schema summaries, metadata uniqueness, sitemap paths, a 2,000-operation synthetic index, the multi-service route tree), the artifact boundary (missing, malformed, unsupported, mismatched, and inconsistent artifacts fail with actionable messages that never contain machine paths), the theme helpers (cookie parsing and return-path confinement), and rendering (semantic queries over the operation, home, reference, service, and group pages, hostile strings as text, deep-link ids, landmarks, compact navigation above 150 operations, and jest-axe). Three fixtures live under `tests/fixtures/reader`: `testinbox` (25 operations, the production-realistic contract), `edge` (hostile strings, slug collisions, long names, many parameters and responses), and `multi` (two documents under `apis/v1/`, a shared tag name, and a duplicated `operationId`). Each commits its `.specra/artifacts`, and `tests/reader/fixtures.test.ts` rebuilds them through the packaged CLI so the committed bytes can never drift.

Schema rendering (SPEC-005) has its own layers. `tests/fixtures/schemas/corpus.ts` is a canonical corpus built directly from model-v1 nodes (primitives, 20/200-property objects, deep nesting, direct/indirect/array/composed recursion, allOf, oneOf ×3 and ×20, anyOf, not, discriminator, tuple, dictionary, boolean true/false, type-less, a 300-value enum, a read/write-mixed object, and hostile names including a 2,000-character key, bidi and zero-width characters, and prototype names), so renderer tests never parse OpenAPI. `tests/reader/schema-view.test.ts` asserts the projection semantically (labels, required state, locators, omission by context, budgets, recursion markers, discriminator mappings); `tests/reader/schema-rendering.test.tsx` renders the components in jsdom with jest-axe (native disclosures, concise summary names, variant anchors, omission notes, inert hostile strings, bounded DOM); `tests/reader/schema-fuzz.test.ts` projects 60 seeded random schema graphs with arbitrary cycles and hostile keys and proves termination, budget, determinism, locator round-trips, and a 10,000-deep inline chain without stack overflow; `tests/performance/schema-render.test.ts` (performance job) records projection time, render time, view nodes, DOM elements, and HTML bytes for representative shapes into `schema-measurements.json`, which CI uploads with the performance evidence.

Browser coverage runs against `next start`: `tests/e2e/reader.spec.ts` (project `chromium-desktop`) and `tests/e2e/reader-mobile.spec.ts` (project `chromium-mobile`, Pixel 5 profile) use the TestInbox fixture on port 3100 with `SPECRA_SITE_URL` set, and a second instance of the same build serves the edge fixture on port 3101 for end-to-end XSS assertions (title, headings, server URLs, no dialogs or page errors). The desktop suite's schema cases prove keyboard operation of native disclosures (Enter and Space, focus retained), discriminator anchors, the focused view with its trail, `noindex` and canonical metadata, redirects for malformed or unknown `?schema=&at=` queries, the request/response difference of one referenced schema, inert hostile names, bounded enums, 250-property and 25-variant states, the depth cut-off, forced-colors outlines and guides, reduced motion, and no-script expansion; the mobile suite adds 375 and 320 px reflow with touch-sized summaries and bounded indentation. The desktop suite also proves the CSP on prefetch-shaped requests, the `/theme` method, origin, and open-redirect rules, the server-rendered 404 and theme form without JavaScript, the forced-colors focus outline, and the backdrop blur; the mobile suite covers the drawer, 320 CSS px reflow, touch-size theme buttons, and the no-script fallback link that reveals the sidebar. The right-to-left override character in the edge fixture is asserted to survive as data (jsdom) rather than being stripped; the browser leaves its rendering to the platform.

Visual baselines live in `tests/visual/__screenshots__` and are generated on Linux, the CI platform, so macOS renderings never become the reference. To update them, run the `visual` project in a Linux container with `--update-snapshots` (`scripts/update-visual-baselines.sh`), review every changed image against the design contract, and commit the images with the change that caused them. Screenshots use the self-hosted fonts, fixed viewports (1440×900, 1366×768, 375×812, plus 320×640 for the narrow edge state), disabled animations, and a hidden caret; the difference policy is `maxDiffPixelRatio: 0.01` and `maxDiffPixels: 2500` together, so anti-aliasing drift passes while a moved element fails. The edge fixture supplies the long-identifier, many-responses, and schema-shapes baselines, plus the SPEC-005 schema states: simple object (light and dark), oneOf with discriminator and a recursion marker, allOf and deep nesting (dark), the focused view of a 250-property object, the request/response context difference, and the complex schema on mobile at 375 and 320 px. The container runs as `linux/amd64` to match the GitHub-hosted runners. Never regenerate a baseline to make a failing test pass without recording why the rendering changed. SPEC-007 added the header search control to every page, so every page baseline changed by that control alone and was regenerated after review; the nine `search-*` images are new. SPEC-006 regenerated every baseline: the sidebar became the composed navigation (authored sections above the API groups on every page), the header gained the `Docs` tab, and the theme tokens were consolidated with `light-dark()`; the twelve `docs-*` images are new.

## Performance evidence

`tests/performance/ingestion.test.ts` runs each workload in a fresh Node process through `ingestion-runner.mjs` with the ingestion host's heap hint (`--max-old-space-size=2048`) and prints input size, operation and schema counts, wall time, peak RSS (`process.resourceUsage().maxRSS`), and artifact size; the same measurements are written to `tests/performance/measurements.json`, which the CI performance job uploads as the `performance-evidence` artifact. The budgets are generous regression ceilings (60 s for the original shapes, 15–20 s for the parser-shape cases, 2 GiB RSS) that catch catastrophic behaviour; the printed numbers are the evidence used to justify the documented limits. The cases prove accept/reject boundaries rather than a single success claim: 10,000 lean operations and 6,000 rich operations are accepted, 10,000 rich operations and 10 MiB of retained text are rejected at the model budget, an 11 MiB source is rejected before parsing, one schema with 40,000 properties is accepted and one with 100,000 rejected in both JSON and YAML (the wide-mapping shape that a quadratic duplicate-key check made pathological), two node-dense 9 MiB documents (18 MiB total) parse within the heap ceiling, 2,000 multipart encodings and 20,000 discriminator variants normalize in linear time, and the packaged CLI builds a 10,000-operation project at the default 30 s source timeout. `packages/cli/src/build.test.ts` and `cli-subprocess.test.ts` additionally prove `INGESTION_TIMEOUT`, SIGINT cancellation, and abort-signal cancellation while a genuinely slow ingestion is running, and that no staging or previous artifact directory survives a failed or cancelled build.

`tests/performance/search.test.ts` measures projection, indexing, serialization, artifact and gzip bytes, hydration, and golden-query latency for the TestInbox fixture, a 1,000-page site, a 10,000-operation contract, and both combined (large projects are built by the packaged orchestrator in a fresh process); measurements go to `tests/performance/search-measurements.json`. `tests/search/relevance.test.ts` runs the committed golden corpus against the committed TestInbox search artifact.

`tests/performance/content.test.ts` generates a 1,000-page site (20 sections, six highlighted TypeScript blocks, a table, a callout, and steps per page) and builds it through the packaged orchestrator in a fresh process, then renders the largest page and counts the navigation entries; it records build time, peak RSS, `content.json` size, and page HTML size in `tests/performance/content-measurements.json`. Ceilings are 120 s, 2 GiB, and the 200 KiB page budget.

## Manual checks

Before releasing UI slices, follow the accessibility matrix in [performance and accessibility objectives](performance-accessibility.md). Security reviewers manually inspect diagnostics/logs for secret leakage. OpenAPI reviewers compare normalized results to 3.0 and 3.1 normative semantics. Performance reviewers record hardware, runtime, input size, wall time, and peak RSS.
